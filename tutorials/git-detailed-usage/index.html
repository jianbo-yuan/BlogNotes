1. Git 解决什么问题

写代码（或论文、博客）时最原始的版本管理是这样的：

Git 做的事情是把”每次保存时的完整状态”变成一条提交链，每个提交（commit）记录：改了什么、为什么改、谁改的、何时改的，并且几乎不占额外空间（只存差异）。由此你获得三种能力：

  • 时间旅行：任意两个版本之间自由切换、对比
  • 平行宇宙：分支（branch）让你同时维护多条开发线互不干扰
  • 协作与备份：远程仓库实现多人协作和多机同步

和”网盘同步”（如 Unison，见Unison 同步教程）的本质区别：Unison 镜像的是当前这一刻的两端状态，Git 保存的是全部历史。两者配合使用：Unison 管分钟级的”改完立刻能跑”，Git 管小时级的”这是一个能用的版本”。

2. 核心模型：三个区域

90% 的 Git 命令都可以用一张图解释。Git 把你的文件分为三个区域：

对应文件的三种状态：

状态 含义 所在区域
Modified（已修改） 改了，还没 add 工作区
Staged（已暂存） add 过，还没 commit 暂存区
Committed（已提交） commit 过，进了历史 本地仓库

为什么要设计”暂存区”这个中间层？因为它让你能把一次大改动拆成多次有意义的提交：改了 5 个文件，其中 3 个是功能、2 个是格式化，分两次 add + commit，历史就干净可读。

5.3 什么时候该开分支

科研代码的实用分支策略（够用就好，不用学企业的 Git Flow）：

  • main：永远可运行。能跑通 baseline 的代码、能出图的实验，才合进来
  • exp/描述：每个实验方向一个分支，如 exp/adamw-lr、exp/diffusion-policy。实验失败就直接扔掉，main 不受污染
  • 临时救火/大重构：fix/xxx、refactor/xxx

6. 远程仓库：多机与协作

6.1 远程的概念

本地仓库和远程仓库是两份独立数据。git push 之前，GitHub 上什么都不知道；git fetch 之后，远程的新提交也只是下载到了本地的 origin/main 分支，还没碰你的 main。

6.2 fetch / pull / push

推荐习惯：push 前先 git pull，让冲突在自己机器上解决，而不是推到一半被拒绝。

6.3 HTTPS 还是 SSH

HTTPS SSH
地址形如 https://github.com/... git@github.com:...
认证 用户名 + token（GitHub 已不支持密码） 密钥对，一次配置永久免密
代理友好 走 HTTP 代理，容易配 需要单独配代理

科研机建议配 SSH：ssh-keygen -t ed25519 后把公钥贴到 GitHub → Settings → SSH keys，具体步骤与Unison 教程第4节完全相同。若所在网络访问 GitHub 不畅，SSH 还有”走 443 端口”的备选方案（~/.ssh/config 里加 HostName ssh.github.com; Port 443）。

7. 撤销与回退：按场景查表

撤销是 Git 最让人害怕的部分，怕的不是命令，是不知道哪条命令影响什么。按文件走到哪一步查下表：

场景 命令 影响
改了，还没 add，想丢弃 git restore <文件> 丢工作区改动（找不回）
add 了，想取消暂存（改动保留） git restore --staged <文件> 无损
commit 了，想改提交信息/补文件 补 add 后 git commit --amend 改写最后一次提交
commit 了，想整体回退（未推送） git reset --soft <hash> 回退提交，改动留在暂存区（无损）
同上，改动放回工作区 git reset --mixed <hash> 无损（默认）
同上，彻底不要了 git reset --hard <hash> 丢弃所有改动（找不回）
已推送到远程，要撤销某次提交 git revert <hash> 生成一个”反向提交”，历史安全
删了分支/坏了想找回 git reflog 见 8.4 节
清理未跟踪的文件 git clean -n（预览）/ git clean -fd（真删） 删除未跟踪文件（找不回）

三条铁律：

  1. 已推送的提交用 revert，不用 reset。reset 是篡改历史，别人拉取会一团糟；revert 是新增一个抵消提交，历史只增不改
  2. reset --hard 和 clean -fd 动手前先 git status 确认没有未保存的心血
  3. 只要提交过，几乎没有真正丢失的代码（reflog 兜底，见 8.4）

10. README 规范：仓库的门面

Git 管住代码”改没改”，README 说明代码”是什么、怎么跑”。它是仓库里唯一保证所有人——包括三个月后的你自己、接手项目的师弟师妹、想复现你结果的审稿人——都会打开看的文件。

科研代码 README 的检验标准只有一条：换一台新机器、一个新人，只看 README 能不能把项目跑起来。

10.2 写作六原则

  1. 命令必须逐条可复制执行。不写”安装相关依赖”，写 pip install -r requirements.txt；不写”修改配置文件”，直接给出要改的行和示例值
  2. 版本写具体。”Python 3.10”而不是”Python3”，”CUDA 12.1”而不是”配好 CUDA”——版本差一位往往正是跑不通的根源
  3. 硬件门槛明示。显存（”24GB 可跑 baseline，13GB 只能跑小号消融”）、是否需要实机/特定驱动/特定操作系统
  4. 给出期望输出。跑成功应该看到什么（终端打印 SR 0.82、生成 outputs/ 目录），让使用者能自行判断成败，而不是对着无报错的卡死界面猜
  5. README 与代码同生命周期。改了运行方式不同步改 README，等于文档造假。把”README 是否需要更新”列进每次提交前的检查（见 10.3）
  6. 别把 README 当公告板。TODO、失败实验记录、私人笔记放 docs/ 或 issue，README 只保留”新人 5 分钟能跑起来”所需的最小集合

关于 requirements.txt 的一个细节：手写关键依赖（torch、numpy 等及版本号）比 pip freeze 全量导出更友好——全量导出会把本地环境几百个间接依赖全部锁死，换平台、换 Python 小版本经常装不上。

12. 常见报错速查

报错/现象 原因与解法
rejected - non-fast-forward 远程有你没有的提交。先 git pull 再 push
fatal: not a git repository 当前目录不是仓库。cd 到项目根目录，或忘了 git init/clone
Permission denied (publickey) SSH 密钥未配置或未加入 GitHub。见 6.3 节
Authentication failed（HTTPS） GitHub 不再支持密码，改用 Personal Access Token 或换 SSH
合并时 CONFLICT 见下方冲突解决流程
detached HEAD 警告 checkout 了提交/标签而非分支。要保存改动就 git switch -c 新分支名
Another git process seems to be running 上次操作崩溃留下了锁文件。确认没有 git 进程后删 .git/index.lock
Windows 下文件全显示被修改 行尾问题。见 3.3 与 9.2 节
