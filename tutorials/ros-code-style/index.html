ROS编程规范

编程规范 机器人开发 ROS ROS2
科研工具 编程类
发布日期:   2026-08-30

1. 为什么 ROS 需要单独一套规范

通用语言规范（C++ 规范、Python 规范）管的是”怎么写好一个类”；ROS 规范管的是”怎么把一堆节点组装成能长期跑的机器人系统”。ROS 项目的死法通常不是某个类写烂了，而是：

  • 话题名一半驼峰一半蛇形，/Hand_state 和 /hand_states 并存，谁能记得住
  • 参数硬编码在节点里，换个机器人要改源码重编译
  • 回调里做阻塞等待，整个节点卡死，连带看门狗失灵
  • 节点间该用服务的地方用了话题，靠”发两次才生效”的玄学时序苟活

ROS1（Noetic）已于 2025 年停止维护，本文以 ROS2（Humble / Jazzy） 为基准，ROS1 差异处单独标注。语言规范仍以前两篇为准，本文只讲 ROS 特有的部分，C++ 与 Python 两种风格并列给出。

2. 包与工作空间结构

2.1 工作空间

规范：

  • 按功能分层分包，不按”节点”分包。驱动、控制、技能各一层，层与层之间靠接口包（*_interfaces）解耦
  • 自定义消息必须独立成接口包，避免”驱动包里定义消息、控制包去 include 驱动”造成的依赖纠缠
  • build/、install/、log/ 进 .gitignore，只提交 src/
  • 日常构建：colcon build --symlink-install（Python/launch 改动免重编）；构建完记得 source install/setup.bash

2.2 包结构（以 ament_cmake 混合包为例）

package.xml 规范：依赖必须声明全（build/depend/exec/test 分清楚），漏写依赖在本机能编过、到 CI 或别人机器上就挂——这是 ROS 项目最常见的”在我电脑上没问题”。

3. 命名规范（ROS 特有）

ROS 命名全部遵循一个原则：全小写蛇形（snake_case），任何地方不用驼峰。

对象 规范 示例
包名 蛇形小写 + 前缀 myrobot_drivers、dexhand_bringup
节点名 蛇形小写，体现功能 hand_driver_node、grasp_planner
话题名 蛇形小写，名词或状态 /joint_states、/hand/cmd_force
服务名 蛇形小写，动词短语 /calibrate_fingers、/set_grasp_mode
动作名 同服务 /execute_grasp
参数名 蛇形小写 control_rate_hz、max_torque_nm
消息类型 大驼峰.msg HandState.msg、GraspResult.msg
消息字段 蛇形小写 joint_positions、is_grasped
坐标系 蛇形小写 + tf 前缀 base_link、left_hand_base、camera_color_optical
服务文件 大驼峰.srv，动宾结构 CalibrateHand.srv

加分习惯：

  • 话题语义分层：/hand/state、/hand/cmd_force、/hand/errors——命名空间即文档，ros2 topic list 一眼看清系统结构
  • 单位进名字：control_rate_hz、max_torque_nm、timeout_ms，与 C++ 规范同一条心法
  • 真假消息类型命名：HandState（状态名词）、HandCommand（指令名词），别出现 HandStateMsg2

4. 通信机制选型

写节点前先想清楚数据该走哪条通道，选错通道返工成本极高：

机制 语义 什么时候用 什么时候别用
Topic 异步、连续流、一对多 传感器数据、状态广播、控制指令流 请求-响应语义（会用”等话题”这种丑陋 hack）
Service 同步、一问一答、短耗时 触发动作、查询配置、开关 超过 ~100ms 的操作（阻塞调用方）
Action 异步、可取消、有进度反馈 长任务：导航到点、完整抓取流程 简单的一问一答
Parameter 配置，非通信 速率、增益、话题名等运行参数 高频变化的数据流

两条经验：

  • 控制指令流用 Topic 不用 Service：1kHz 的指端力矩指令如果走 Service，网络往返时延直接毁掉控制带宽
  • 长任务一律 Action：抓取流程走 Service，中途想取消只能杀节点

5. C++ 节点规范（rclcpp）

5.1 标准骨架

骨架里的硬规矩：

  • 一节点一类一文件，类名与节点名对应；main 只有 init/spin/shutdown 三行
  • 硬件/算法对象与 ROS 类型解耦（例中 HandDriver 不含任何 ROS 头文件）——这使核心逻辑可以脱离 ROS 单测，也是 pybind11 桥接的前提
  • 回调要薄：只做数据搬运，重活交给成员方法；回调里严禁阻塞（sleep、等待 Service、慢 IO）
  • 定时器用 create_wall_timer，禁止 while (rclcpp::ok()) { ... sleep(1); } 手搓主循环
  • 所有成员变量类内初始化、智能指针用 SharedPtr 类型别名（rclcpp 惯例）

5.2 生命周期节点（需要受控启动时）

控制类节点建议实现 LifecycleNode（on_configure/on_activate/on_deactivate/on_shutdown 四态），让”参数加载完、订阅建好、确认硬件在线”之后才允许发指令——上层可以统一编排所有节点的激活顺序，避免半初始化节点往总线上发垃圾。

6. Python 节点规范（rclpy）

同样的骨架，Python 风格如下（与 C++ 版逐条对应）：

Python 侧额外规矩：

  • 私有成员统一 _ 前缀；类型注解按Python 规范全覆盖
  • 回调里同样禁止阻塞；需要调用外部系统（模型推理、HTTP）时，把回调数据丢进 queue.Queue，由独立线程消费
  • 多回调并发：默认单线程执行器按顺序执行；确实需要并发时用 MultiThreadedExecutor + ReentrantCallbackGroup，并自己保证共享状态的线程安全
  • 入口脚本记得 chmod +x 并在 setup.py 的 entry_points 注册，而不是裸 python xxx.py 跑

C++ / Python 怎么分工

层 语言 理由
硬件驱动、实时控制 C++ 确定性、延迟（见 C++ 规范第12节）
策略推理节点 Python（或 C++ 桥 Python） 生态在 PyTorch 侧
任务编排、技能逻辑 Python 迭代快，容错高
自定义消息 独立接口包 双语言都要能 import

7. 参数与配置管理

一切可变的量都是参数，参数都有默认值，参数最终都以 yaml 落地：

规矩：

  • 先 declare_parameter 再使用，禁止直接 get_parameter 未声明参数（ROS2 默认会抛异常）；默认值让节点”零参数也能跑起来”
  • 参数名、yaml 键名、launch 传参三处拼写完全一致（蛇形小写）
  • 运行时改参数要走 set_parameter 或 ros2 param set，不要设计成”重开节点才能生效”再配上”忘了重启”的经典事故
  • ROS1 差异：rospy.get_param("~rate", 500) 无声明概念，靠自觉补齐默认值

8. 自定义消息规范

规矩：

  • 带时间戳的数据流消息必须有 header（对齐、录制、回放全靠它）
  • 数组：长度固定用 float64[N]，长度可变才用 float64[]；控制相关消息一律定长
  • 服务响应必带 success + message，调用方不需要 print 就知道为什么失败
  • 消息一旦发布给别人用，只加字段不改不删（兼容性）；要大改就发新消息 HandStateV2——和 git 历史只增不重写是同一个道理
  • 改了 msg/srv 必须重编接口包，下游 colcon build --packages-select myrobot_interfaces 再编

9. Launch 与启动管理

启动文件用 Python 版（可断点、可逻辑分支，XML 版不推荐新写）：

规矩：

  • 节点参数一律从 yaml 读，launch 只传”这次启动有什么不同”（配置文件路径、真机/仿真开关）
  • name= 与 yaml 中的顶层键严格一致——名字对不上，参数静默不生效，这是 ROS2 排障榜第一名
  • 复杂系统：一个 bringup.launch.py 顶层编排各子系统 launch，机器人一条命令全起
  • 调试口诀：ros2 node list / ros2 topic list / ros2 param list /节点名 / ros2 topic echo /话题 --once 四连

10. TF 坐标规范

  • 坐标系名蛇形小写；约定俗成：base_link（机身）、world/map（全局）、*_optical（相机光学系，Z 朝前）、左右加前缀 left_/right_
  • 机体坐标系右手系、X 前 Y 左 Z 上；光学系才允许 Z 前
  • 变换查询一律走 tf2 缓冲（tf2_ros::Buffer + TransformListener），带超时等待；禁止手工抄数位姿
  • 静态变换（手眼标定结果）用 static_transform_publisher 或 URDF 里的 <joint fixed>，写进 URDF/launch，不写进代码
  • 一条链上只能有一个权威发布者：谁发布 hand → base_link 由 bringup 层唯一决定，多处发布同一变换 = TF 树碎裂

11. 时间与日志

时间：

  • 节点内取时间一律用节点时钟：C++ now()、Python self.get_clock().now()——仿真时 use_sim_time 才能全局生效，std::chrono::system_clock 或 time.time() 会在仿真里直接错乱
  • 回放 rosbag 时钟跳变、控制周期计时都要走节点时钟

日志：

  • C++ 用 RCLCPP_INFO/WARN/ERROR(get_logger(), ...)，Python 用 self.get_logger().info/warning/error——禁止 printf/print（无级别、不可控、进不了 rosout 聚合）
  • 循环高频路径只允许低级别日志在调试期打开；ros2 topic echo /rosout 按节点/级别过滤
  • 关键状态变迁必须留一条 INFO（模式切换、上下电、错误进入/恢复），半年后看日志回放事故现场全靠它们

12. QoS 与实时性

ROS2 的 QoS 决定”数据丢了怎么办”，默认全 Reliable 在传感器流上会酿灾难：

数据类型 QoS 理由
传感器/控制指令流 SensorDataQoS()（best_effort + depth 10） 丢一帧无害，堵一拍致命；订阅端 QoS 必须匹配
状态/事件通知 reliable + transient_local（”迟到的订阅者也能收到最后一条”） 新节点上线立即拿到当前模式/状态
服务/action 默认 —

实时性（承接 C++ 规范第12节）：

  • 控制节点回调即控制周期：回调内禁堆分配、禁阻塞调用、禁异常
  • 跨线程数据传递用消息队列（订阅/发布本身就是无锁队列），别在节点里手搓共享内存 + 锁
  • 大数据（点云、图像）考虑组件化节点同进程组合（ComposableNode），进程内通信零拷贝；Python 节点不参与实时链路
  • 看门狗独立成节点：监控 /joint_states 等心跳话题，超时直接发急停——上层全卡死时它必须还活着

子系统 录制回放 ros2 bag record → 回放比对
全系统 带仿真跑 bringup 仿真 + ros2 topic hz 查频率

14. 总结

ROS 规范一句话版：

  1. 结构：按功能分包 + 接口独立成包 + yaml 管参数
  2. 命名：全蛇形小写、单位进名字、话题分层命名
  3. 骨架：一节点一类、回调薄、定时器驱动、硬件逻辑与 ROS 解耦
  4. 选型：流走话题、问答走服务、长任务走动作、配置走参数
  5. 纪律：QoS 显式、节点时钟、日志框架化、TF 唯一权威
  6. 分层：实时与驱动用 C++、策略与编排用 Python、消息双语言共享

与前两篇构成完整链条：语言规范（怎么写好一个类）→ 本文（怎么组好一个系统）→ Git/Unison 规范（怎么管好一个仓库、同步好两端）。机器人项目按这套从下往上搭，新节点接入成本是一条 launch 文件，而不是考古一个 main_final.py。
