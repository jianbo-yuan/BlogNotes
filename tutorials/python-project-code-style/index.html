Python工程编程规范

编程规范 Python 工程实践 Lint
科研工具 编程类
发布日期:   2026-08-30

1. 为什么需要编程规范

科研代码的典型命运是：写的时候只有自己懂，三个月后自己也不懂，交接时重写比重读快。编程规范的作用不是审美，而是把”能跑”变成”能被维护、能被复现、能被交接”。

规范解决三类问题：

问题 没有规范时的样子 规范带来的
可读性 data2_new_final.py、驼峰蛇形混用 命名即文档，看名字知用途
可维护性 路径硬编码、全局变量满天飞 改一处不影响全局
可复现性 换台机器跑不起来、结果随缘 依赖、配置、种子全部显式

本文基于社区事实标准（PEP 8 + Google Style）整理，优先给结论和工具，不纠结学派之争。原则：工具能自动解决的交给工具，工具管不了的靠约定。

2. 工程结构规范

2.1 推荐结构（src layout）

要点：

  • scripts/ 放入口、src/ 放逻辑。入口脚本只做”解析参数 → 调用库函数”，不超过几十行；核心逻辑全部在包里，可被测试和复用
  • 数据、权重、产物绝不进 git（.gitignore 已排除）
  • 不要出现 src/v1/、src/v2/、src_final/——版本管理是 git 的工作，不是目录结构的工作

3. 命名规范

Python 的命名约定全网统一，没有争论空间，照做即可：

对象 规范 示例
模块/文件 蛇形小写、简短 data_loader.py、policy.py
函数/方法 蛇形小写，动词开头 load_dataset()、compute_loss()
变量 蛇形小写 batch_size、lr_schedule
常量 全大写蛇形 MAX_GRIPPER_FORCE、LOG_DIR
类 大驼峰（PascalCase） DiffusionPolicy、DataLoader
异常类 以 Error/Exception 结尾 CalibrationError
类型变量 大驼峰或单大写字母 TensorT、T
私有成员 前置单下划线 _check_input()、self._cache
包名 蛇形小写、短 myproject（不用连字符和中文）

命名的心法：

  • 名字回答”是什么”，不回答”怎么来的”。grasp_success_rate 好，res2 差；tmp、data、flag 一律禁用
  • 布尔值读起来像判断：is_trained、has_touch、use_cuda
  • 不要缩写过头：cfg 可以（约定俗成），cltr 不行（controller？）
  • 长度适中：作用域越大的名字越要完整；循环计数器 i、j 是唯一合法的短名

5. import 规范

顺序（ruff 的 I 规则自动排序，无需手工管）：

规则：

  • 禁止 from xxx import *——污染命名空间，工具无法分析
  • 相对导入只在包内部用（from . import utils），入口脚本一律绝对导入
  • 不要在 import 处做副作用（读写文件、连设备）；模块导入应当轻快
  • 删掉 IDE 自动添加但没用的 import（ruff 的 F401 会抓）

注解规范的心法：公共 API（被别人调用的函数）必须注解；内部辅助函数至少注解参数。科研数值代码里注解还能防一类经典 bug——ndarray 和 Tensor 混着传。

7. 文档字符串

公共函数、类、模块必须有 docstring，格式统一用 Google 风格（可读性最好，IDE 提示友好）：

规则：

  • 一行摘要开头：祈使句、句号结尾、不超过 79 字符
  • 注释写为什么，代码写是什么。i += 1 # i 加一 是废话；# warmup 阶段不更新目标，防止早期策略抖动 是好注释
  • 私有函数可以只写一行摘要
  • TODO 格式统一：# TODO(yourname): 说明 <相关 issue 编号>

8. 函数与模块设计

8.1 函数设计五条

  1. 一个函数做一件事。名字里出现”和/以及/然后”就该拆
  2. 短。超过 60 行考虑拆分；超过 150 行必须拆
  3. 参数少。超过 5 个考虑收拢成 dataclass 配置对象
  4. 无副作用优先。同样输入永远同样输出（方便缓存与测试）；必须修改状态时在名字里体现（update_cache 而不是 get_cache）
  5. 不写旗标参数。process(data, flag=True) 走两条逻辑路，不如拆成两个函数

8.2 用 dataclass 管配置

配置散落成一堆函数参数是烂代码的前兆，用 dataclass 收拢：

8.3 模块级代码的规矩

禁止：模块顶层直接 torch.cuda.init()、连设备、读文件——你的模块被 import 时（比如跑测试时）会连带触发这些动作。

8.4 避免全局可变状态

全局变量改成两选一：只读常量（模块级大写命名），或收进类实例。global x 语法在整个项目里应当出现零次。

9. 配置与路径管理（科研代码重灾区）

三条铁律：

1. 路径绝不硬编码，更绝不写死绝对路径

2. 超参数进配置文件（yaml），不进代码

入口脚本接 argparse 或 hydra，命令行参数可覆盖 yaml 默认值。

3. 命令行脚本必须有 --help

10.2 异常处理

规则：

  • 不许裸 except:，最少 except Exception as e 且记录 e
  • 捕获要精准：知道会抛什么才捕什么
  • 数据校验类错误尽早抛（fail fast）：形状、维度、范围在函数入口检查

11. 测试

不需要 TDD 教条，但核心数值逻辑必须有测试——数据处理、几何计算、评估指标，这些错一行整个实验结论作废：

运行：pip install pytest && pytest tests/ -v。什么时候写测试：写完一个纯函数（无 IO、无 GPU）后顺手写三个用例（正常、边界、异常）；训练循环不强行测。

12. 科研代码专项规范

工程规范之外，实验代码有自己的一套”复现性规范”：

  1. 随机种子集中管理且显式传递：

每个实验的 seed 写进 yaml 并记进产物目录名。

  1. 每次运行留指纹：输出目录带时间戳和配置快照 outputs/2026-0830-1421-seed42/，内含完整 yaml、git commit hash、最终指标。半年后翻结果目录，还能知道它是哪个 commit 跑出来的：
  1. notebook 是探索工具，不是交付物。探索完把有效逻辑落成 src/ 里的函数 + scripts/ 里的入口，notebook 清空输出后再提交（.gitignore 或 nbstripout 处理）
  2. 设备相关代码隔离：torch.device 从配置传入，不在函数内部写死 "cuda"；cpu/cuda 都能跑的代码调试成本低一个量级
  3. 实验结论三件套同步：代码（git tag）、配置（yaml 快照）、产物（输出目录）指向彼此，缺一不可

14. 总结

Python 规范的优先级排序，精力有限时从上往下做：

  1. 结构：scripts 入口 + src 逻辑 + 配置 yaml——这决定项目能不能长大
  2. 命名：零成本、收益最大的一件事
  3. 工具：ruff + pre-commit 装上，风格之争永久消失
  4. 类型注解 + docstring：公共 API 必须有
  5. 可复现三件套：seed 显式、运行留指纹、配置即实验

规范不是文档里的教条，而是 pre-commit 钩子里自动执行的事实。写代码时多花 5% 的时间遵守规范，三个月后省下 95% 的重构时间。
