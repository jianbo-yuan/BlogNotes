Cpp工程编程规范

C++ 编程规范 CMake 机器人开发
科研工具 编程类
发布日期:   2026-08-30

1. 为什么 C++ 更需要规范

Python 写坏了，运行时抛个异常还能看见；C++ 写坏了，常常是未定义行为（UB）——不报错、出鬼结果、偶发崩溃、release 和 debug 行为不一样。机器人场景下 C++ 又恰恰承担最要命的部分：实时控制循环、硬件接口、与 Python 策略层的桥接。

所以 C++ 规范的目标比 Python 更进一步：不仅是”可维护”，还要在编译期把错误拦下来，让错误不可能藏进控制循环里。本文以社区事实标准（Google C++ Style 为主干、结合 ROS 生态惯例）整理，重点关注：

  • 资源与生命周期（C++ 出事故的头号来源）
  • 头文件与依赖管理（编译慢、耦合重的根源）
  • 实时控制代码的专项纪律

2. 工程结构规范

要点：

  • include/ 与 src/ 分离：对外暴露的 API 头文件放 include/myproject/，只在项目内部用的头文件直接放 src/ 里。这决定了下游能不能干净地链接你的库
  • 一个类一对 .hpp/.cpp（小工具类可以 header-only）
  • 头文件名与类名一致：HandDriver → hand_driver.hpp（ROS/Google 惯例为蛇形文件名）

3. 命名规范

C++ 命名流派多（Google、LLVM、Boost 各一套），选一套、全项目统一即可。机器人领域 Google 风格占主流（ROS 官方也基于它），推荐直接采用：

对象 规范 示例
文件名 蛇形小写 hand_driver.hpp、policy_server.cpp
类型（类/结构体/枚举/别名） 大驼峰 + 名词 HandDriver、GraspResult
函数/方法 大驼峰，动词开头 SendCommand()、GetState()
常量与枚举值 k 前缀大驼峰 kMaxGripperForce、kTimeoutMs
局部变量/参数 蛇形小写 torque_limit、recv_bytes
类成员变量 蛇形 + 尾下划线 torque_、serial_port_
结构体纯数据成员 蛇形小写（无尾缀） msg.joint_pos
命名空间 全小写单词，无缩进 namespace myproject
宏 全大写（但尽量不用宏） MYPROJECT_VERSION

三个约定俗成的心法：

  • 看名字知角色：torque_ 一眼是成员、kTimeout 一眼是常量、SendCommand 一眼是方法——不需要来回翻声明
  • 结构体（struct）只放数据不加行为时用蛇形成员，与类区分开
  • 单位写进名字：force_n（牛）、period_ms、rate_hz——机器人代码里单位混乱是经典事故源

4. 头文件规范

4.1 基本 discipline

规则：

  • 每个头文件 #pragma once 开头
  • include 顺序固定：本文件对应头（.cpp 里第一个）→ C 标准库 → C++ 标准库 → 第三方 → 本项目（clang-format 的 IncludeBlocks 自动管）
  • 能 #include 就不前置声明（前置声明只用于打破循环依赖时），见 4.2
  • .cpp 里能下沉的 include 绝不上浮到 .hpp——头文件里的每个 include 都会传染给所有下游

4.2 减少头文件依赖

头文件最贵的不是写，是被传染。hand_driver.hpp include 了 <Eigen/Dense>，所有包含它的文件都要重编 Eigen。手段按优先级：

循环依赖是设计问题的信号：A 要 include B、B 要 include A，说明两个类职责纠缠，该拆出第三个（通常是数据类型或接口）放到两者都能 include 的头里。

5. 资源管理：RAII 与智能指针

C++ 事故的头号来源是”资源拿了没还”：new 了没 delete、锁了没解锁、打开了没关闭。现代 C++ 的答案只有两个字：RAII——资源的获取与释放绑定到对象的构造与析构，编译器保证析构一定发生。

5.1 规则零

类的作者把析构、拷贝、移动全部交给编译器自动生成（”rule of zero”），资源全部交给 RAII 类型管理：

资源 裸写法（禁止） RAII 写法
堆内存 new int[64] / delete[] std::vector<int>
单对象 new Hand(cfg) / delete std::unique_ptr<Hand>
文件 fopen / fclose std::fstream / RAII 封装
锁 pthread_mutex_lock std::scoped_lock
socket/串口 open / close 自封装 RAII 类

整个项目里裸 new/delete 的合法出现次数：零。 需要动态多态（基类指针指向派生类）时用 std::make_unique：

5.2 智能指针选型

场景 用什么
默认、独占所有权 std::unique_ptr<T>（零开销，首选）
真正的共享所有权（罕见） std::shared_ptr<T>
观察别人的对象、不拥有 裸指针 T* 或引用 T&（不参与生命周期）
可能悬垂的观察 std::weak_ptr（配合 shared_ptr）

经验法则：先按 unique_ptr 设计，编译器报错了再换。shared_ptr 满天飞的项目，所有权一定是一笔糊涂账。函数参数传递所有权语义要清晰：

5.3 规则五（当类必须手动管理资源时）

如果类真的直接持有裸资源（比如封装 C 库句柄），才需要显式定义”规则五”——析构、拷贝构造、拷贝赋值、移动构造、移动赋值，缺一不可。定义了析构函数的类，编译器不再自动生成正确的拷贝行为，拷贝一个持有句柄的对象 = 句柄被释放两次。

6. const 正确性与接口设计

const 不是装饰，是编译期契约：”这个函数不改你的数据”。全项目 const 正确后，一大类误改 bug 直接绝迹：

接口设计清单：

  • 单参构造函数加 explicit，防隐式转换的意外调用
  • 成员变量一律 private；纯数据聚合用 struct
  • 类内给每个成员默认初始值，杜绝”栈上未初始化读出随机值”这种幽灵 bug
  • 二元接口（send/recv、open/close、start/stop）成对出现在同一个类里，由 RAII 串起来

8. 错误处理策略

C++ 的错误处理没有唯一答案，按场景分层：

错误类型 处理方式 示例
程序员 bug（不可能发生） assert / DCHECK，release 里消失 assert(idx < size())
可预期的运行失败 返回值携带错误 串口超时、文件不存在
无法继续的系统级错误 异常（仅构造函数等无法返回错误处） 配置文件解析失败
致命不变量破坏 std::terminate 级别，明死好过暗错 控制线程数据结构被破坏

实时控制模块禁止异常（见第12节），可预期失败用返回值表达：

三条纪律：

  • 错误必须被处理或被显式传播，吃掉错误码当无事发生是重大事故源
  • 构造可能失败的类：提供 static std::optional<T> Create(...) 工厂或两段式（构造轻量 + bool Init()），别在构造函数里抛异常
  • 日志记录错误时带上上下文（哪个设备、什么指令、错误码数值），排障时间差十倍

12. 实时与安全专项

跑在控制循环（500Hz~1kHz）里的代码有额外纪律，每一条都对应一类真实事故：

  1. 循环内禁止堆分配。new、push_back 扩容、按值传 std::string/vector、流式格式化——都会在不确定的时刻触发不确定时长的分配，甚至触发页错误。进循环前把 buffer 全部 reserve 好，固定大小的循环数据用预分配的 std::array 或成员容器

  2. 循环内禁止异常。异常展开时间不可控。控制模块编译时直接 -fno-exceptions，或约定所有循环内调用都是 noexcept 路径

  3. 日志不得阻塞循环。循环里只往预分配的环形缓冲写字节，专门的日志线程慢慢格式化落盘。直接在 1kHz 循环里 printf/std::cout 是抖动之源

  4. 加锁循环等于埋雷。优先无锁队列（SPSC ring buffer）做线程间数据传递；必须加锁时用 try_lock + 丢弃旧数据策略，宁可丢一帧不能拖一拍

  5. watchdog 必须有。策略层卡死（网络、GPU）时，控制层必须能在超时后自动进入安全态（力矩清零、缓降、抱死）。超时安全逻辑放在最底层、独立于上层逻辑运行

  6. 单位与坐标系统一写死在一个头里。units.hpp 定义 kRadToDeg、各关节坐标系约定。单位换算散落各处的项目，迟早出”力矩大了 100 倍”的事故

  7. 状态机显式建模。enum class HandMode + 转移表，禁止用五个 bool 的组合表达状态（is_running && !is_error && has_init 的第 32 种组合就是事故现场）

规范要点：

  • 桥接层只做翻译，不做逻辑。业务逻辑留在 C++ 核心，Python 绑定和 CLI 一样是薄壳
  • 热路径避免跨语言逐帧调用。Python 里 for 循环调 1000 次 C++ 函数不如把循环下沉到 C++、只往返一次（py::array_t 批量传 ndarray）
  • GIL 与控制线程：C++ 内部线程回调 Python 时注意持锁规则，或干脆用队列单向传递数据

14. 总结

C++ 规范的优先级排序：

  1. 资源全部 RAII，裸 new/delete 归零——这一条消灭一半的事故
  2. const 正确 + explicit + 类内初始化——编译器替你站岗
  3. 头文件纪律（include 下沉、减少传染、拆循环依赖）——项目规模的生死线
  4. 现代 CMake target 化 + clang-format/tidy 上墙——工具管住风格与常见 bug
  5. 控制循环七条禁令——实时系统的安全底线
  6. 纯逻辑（协议、状态机、坐标变换）必须有 GTest，硬件用 mock 注入

与 Python 规范搭配食用：策略训练侧按Python 工程编程规范执行，实时执行侧按本文执行，桥接层两边都保持薄——这就是机器人项目”聪明的算法跑在 Python、可靠的肌肉长在 C++”的完整工程图景。
