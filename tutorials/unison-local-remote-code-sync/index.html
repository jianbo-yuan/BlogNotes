通过Unison实现本地与远程服务器的代码同步

Unison 文件同步 SSH 远程开发 Linux Windows
科研工具 编程类
发布日期:   2026-08-30

1. 为什么需要 Unison

做机器人学习相关开发时，一个非常典型的工作流是：

  • 本地机（Windows，带 IDE、浏览器、文档）：写代码、看论文、画图
  • 远程服务器（Linux，带 GPU、机器人环境、ROS）：跑训练、跑仿真、连机器人

代码在两端都会产生变化：本地改了源码，服务器跑实验生成了日志和结果。把两边的工作区”缝合”起来，就是文件同步工具要做的事。

常见方案对比：

方案 方向 状态记忆 冲突处理 适合场景
scp / sftp 手动单向 无 无 偶尔传一两个文件
rsync 单向 无（靠对比元数据） 直接覆盖 备份、发布，方向明确时
git push/pull 双向 有（版本库） 有（合并） 管代码本身，不适合大文件/产物
SSHFS / 网络挂载 实时 — — 网络稳定、延迟低，断网即瘫
VSCode Remote-SSH 直接在远端编辑 — — 不需要本地副本时最省事
Unison 双向 有（同步档案） 逐文件交互决策 两端都有改动、离线可编辑、需精确控制

Unison 的定位一句话：记住两端上次同步时的样子，之后每次运行，把两端各自的增量变化（新增、修改、删除、重命名）互相传播，遇到同一文件两边都改过的情况，逐个问你怎么处理。

它和 rsync 最本质的区别：rsync 是”把 A 复制成 B”，Unison 是”把 A 和 B 汇合到同一个最新状态”。代码开发恰恰是双向都有改动的场景，所以 Unison 比 rsync 合适。

2. 工作原理：两个副本 + 一份档案

理解 Unison 的行为，只需要记住一个模型：

每次同步时，Unison 做三件事：

  1. 扫描两端目录，得到当前状态
  2. 与本地保存的档案对比：相对上次同步，谁变了？
    • 只有 A 变了 → 把变化传播到 B
    • 只有 B 变了 → 把变化传播到 A
    • 两边都变了（内容不同）→ 冲突，逐个询问
    • 两边都没变 → 跳过
  3. 同步完成后，更新档案

由此推出几个重要性质：

  • 删除会被传播。上次同步后你删了本地某个文件，下次同步时服务器上的同名文件也会被删——这不是 bug，是设计
  • 重命名能被识别。档案里记着内容指纹，文件改名不会触发”删一个 + 传一个大文件”
  • 档案丢了 = 失忆。档案损坏或被删后，Unison 视作”第一次同步”，任何两端内容不一致的文件都会变成冲突（内容一致的会自动跳过）

档案保存在各自主机的 ~/.unison/ 目录下（Windows 是 %USERPROFILE%\.unison\），文件名是两个 root 路径的哈希。不要把它加进同步目录自己。

3. 安装：两端都要装，版本必须一致

Unison 是 C/S 结构的：本地跑一份，通过 SSH 在远端再拉起一份。两端必须安装同一个主次版本（例如都是 2.53.x 可以互通，2.52 对 2.53 不行），否则连接时会直接报版本不匹配错误。装完第一件事就是核对两边 unison -version 输出一致。

实际项目建议直接用下面这套配置（逐行注释）：

几个选项展开说明：

  • ignore = Name xxx：按文件名/目录名匹配，任意层级生效；花括号 {a,b,c} 表示”或”
  • ignore = Path xxx：按相对 root 的路径匹配，更精准（如只忽略根下的 outputs，不影响别处同名目录）
  • copyonconflict = true：冲突时不强迫你二选一，Unison 会保留双方版本，赢家占原名，输家生成 原文件名.unisonconflict 后缀的副本，事后可以自己 diff 取舍。对代码来说”宁可多一个文件，不可静默覆盖”
  • perms = 0 + dontchmod = true：Windows↔Linux 同步的双件套，不开的话你会看到大量诡异的权限更新提示

5.3 .git 目录要不要同步？

两种流派，按需选：

  1. 同步整个项目但排除 .git（ignore = Name .git）：两边各自是独立工作区，远端单独 git init/clone。优点是简单隔离；缺点是两边 .git 状态会逐渐分叉（本地有 commit 远端没有），merge 时容易懵，只适合”本地写、远端跑”的单向为主的场景
  2. 连 .git 一起同步：两边共享同一个版本库状态，git log/git stash 两端一致。这是双向开发更推荐的方式，但要求两端的 git 行尾配置一致（见第8节踩坑 4），否则每个文本文件都会因为 CRLF/LF 差异被判定为冲突

8. 常见问题与踩坑

1. 报错：两端版本不一致

症状类似 Fatal error: Received unexpected header from the server 或直接提示版本不匹配。解决：unison -version 两边各跑一次，统一到同一版本（见 3.2 的 servercmd 用法）。

2. 每次都提示一堆文件 “changed”，但内容明明没变

最常见的三个原因：

  • 两端时钟偏差：Unison 依赖 mtime 判断改动，两端时钟差几秒就会导致误判。服务器 timedatectl 看 NTP 是否同步，Windows 设置里开启自动时间同步
  • 权限差异（Windows↔Linux 必现）：确认 profile 里有 perms = 0 和 dontchmod = true
  • 时间戳被其他工具改写：某些编辑器、格式化工具会 touch 全部文件。临时用 unison myproject -fastcheck no 强制按内容校验，确认无误后再恢复

4. git 仓库行尾（CRLF/LF）导致满屏冲突

Unison 按字节同步，不做行尾转换。如果本地 Windows git 是默认 core.autocrlf=true（检出成 CRLF），远端 Linux 检出是 LF，同一个文件两端字节不同，每次同步全是冲突。修复（连 .git 同步的场景）：

5. 误删了文件，同步把它也删了

删除传播是设计行为。补救：

  • 若文件在 git 里：git checkout -- 文件 恢复

  • 养成习惯：大批量删除后，第一次同步用交互模式跑，扫一眼删除列表再按 f

7. 大文件 / 数据集同步很慢

Unison 走 SSH 单流，适合代码和小文件；几 GB 的数据集、checkpoint 建议走专门通道（rsync 增量、对象存储、内网 NFS），并用 ignore 把它们排除在双向同步之外。同步前先跑一次 -testserver 和小目录试水，估算速度。

9. 与 git 的分工

Unison 和 git 不互相替代，而是各管一段：

git Unison
管什么 代码的版本历史 工作区的即时镜像
何时用 完成一个逻辑单元后 commit 每次改完想立刻在服务器上生效
大文件 不友好 不适合（走别的通道）
冲突 分支合并 文件级二选一

推荐节奏：本地编辑 → unison 推上去 → 服务器跑 → unison 把结果拉回来 → 阶段性 git commit。Unison 负责”分钟级”的同步，git 负责”小时级”的存档，两边叠加既有速度又有安全感。

10. 总结

Unison 的核心心智模型就三条：

  1. 两个 root + 一份档案：档案记录上次同步状态，据此算出两端各自的增量
  2. 删除会传播，冲突会询问：交互按键 f/>/<，配 copyonconflict=true 保平安
  3. 跨平台三件套：perms = 0、dontchmod = true、统一行尾，Windows↔Linux 同步的坑基本都集中在这

配好一次之后，日常就是一条命令的事。相比每次手动 scp 或者开着 SSHFS 提心吊胆，Unison 是”本地编辑 + 远程算力”这种双栖开发模式里最省心的缝合方式之一。
